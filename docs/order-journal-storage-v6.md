# Optional order journal storage schema 6

Stop every ORDER executor, back up the database, and verify schema version 5 with the persistent evidence-v1 stream migration installed before applying `sql/order_journal_delta_v1.sql` offline. Running executors do not migrate storage. Old schema-5 executors reject version 6 at startup. The current initializer installs schema 5 for a new database and only verifies an existing schema 6. The migration leaves every historical row intact and every account in FULL mode.

Only after paired reads in an isolated environment, a separately authorized operator can set one account_runtime.event_journal_write_mode to BASE_DELTA_V1. Switching that account back to FULL affects only future events. Continue to run schema-6-compatible binaries and repair tools for databases that contain deltas. To deploy a schema-5 binary again, restore a compatible backup or perform an independently verified offline materialization migration. Never rewrite existing event history during routine startup or rollback.

The authoritative order_events primary key and event sequence are unchanged. Each original full internal order document stays a JSON object. A smaller immutable delta is stored as a tagged JSON array referencing one full order event explicitly labeled with the same stream, account and order. The first event after selecting delta mode is a full baseline. Legacy and FULL-mode rows have no per-row stream label and never serve as delta bases. A complete baseline is written at most every 16 per-order events or earlier when a patch would cost more than full JSON. All deltas refer directly to a full baseline. The scoped foreign key protects retained dependencies and an UPDATE trigger guards original rows. The persistent account stream is guarded against replacement while it retains events. A digest binds the original baseline and the reconstructed internal snapshot. New orders, child projections, journal sequence and journal row all commit in the existing transaction.

Legacy events, evidence pagination, immutable source lookup, formal recovery and the terminal repair tool materialize the full historical document before projection or hashing. The sequence-void source remains independent. Raw SQL consumers that previously assumed order_events.document is always a JSON object must use a compatible materializing reader. Old version-specific backfill and timestamp migrations remain confined to their documented source schemas. Retention must preserve every referenced baseline. This does not reduce the separate mutable orders or child projections and does not modify existing journal bytes.
