# ORDER 非阻塞、分批执行与对账退出计划

状态：2026-09-26 已完成代码、文档、独立 PostgreSQL 和 FakeQmt 验收。业务库未迁移，券商模拟盘验证不包含在本轮。

## 目标及约束

QMT 同步 API 继续在 QMT 调度上下文执行；调度线程只做必要 QMT 调用和短时内存操作。数据库、日志、等待、恢复和状态归并移至后台。保留订单与撤单幂等、UNKNOWN 不盲重发、普通/算法/原生篮子交易语义、既有三个查询接口、Python 3.6.8、独立 GBK 策略、中文注释和 Last modified。

保留固定 qmt_order schema，通过 pg_database 隔离环境；启动根据实际 account_id 幂等创建账户记录，不能重置 event_seq 或执行权。DDL 只在外部 SQL 文件，业务库迁移是显式部署步骤。

## P0：参数、状态字段及迁移

新增运行参数，启动读取并冻结，小写优先，兼容 QMT 面板执行前/init 前注入，非法值启动失败，并写入文件头和启动日志：

| 参数 | 默认值 | 计数口径 |
| --- | --- | --- |
| submit_batch_size | 10 | 每轮实际派发的业务订单数，篮子算一笔 |
| cancel_batch_size | 10 | 每轮实际 QMT 撤单动作数，任务和子委托各算一次 |
| reconcile_batch_size | 100 | 每批进入对账的业务订单数 |
| schedule_budget_ms | 50 | process_http_requests 整个回调预算 |

数量仅为上限，同时受时间预算限制；剩余工作跨 tick 继续。已开始的同步 QMT 调用不能强制中断。

新增持久 reconcile_pending，区分执行 active、本轮覆盖完整度和是否继续对账。保存最近尝试、最近完整成功、下次到期、事实版本及必要游标。为 QUEUED、可撤候选、pending 到期对账提供匹配索引。提供全新 v2 安装及显式 v1→v2 迁移，旧数据保守回填，启动拒绝不兼容版本。

## P1：线程职责、执行权、日志和启停

- HTTP 线程负责参数校验、持久受理、幂等和数据库查询，允许等待自己的事务；只有提交确认后才返回 202。
- 数据库后台线程负责候选读取、认领、调用结果持久化、回报归并、状态计算、恢复。
- 执行权后台线程独占持有 advisory lock 的专用连接；定期检查并在生成交易授权前核验。HTTP 和 QMT 线程不共享访问该连接。
- QMT 调度线程负责下单、撤单、交易查询、SMART 配置、篮子操作和原生对象快照。不能执行 SQL、等待 DB 结果、调用 Future.result/Event.wait/join，或持有跨 I/O 共享锁。
- 日志后台线程格式化并输出上海时区 console + 每日文件日志。满队列记录丢弃计数，不回退至 QMT 同步输出。
- 用有界普通数据队列通信。交易调用前保证结果缓冲容量；未持久结果保留，DB 故障暂停后续交易调用。回报溢出明确记录缺口并补查。
- QMT 侧检查内存停止标志、实例代次和短期有效授权。授权失效、过期或 DB 异常时暂停交易，不无限复用旧缓存。不宣称 PG 与 QMT 原子提交。
- 初始化检查、账户 upsert、执行权和恢复均在后台；恢复完成前不接受新订单。未配置 PG 保持查询模式。
- stop 先关闭受理/派发并取消定时任务；后台等待在途工作收尾，再释放数据库连接、本机锁和日志资源。QMT stop 回调不能等待后台。清理完成前维持 STOPPING，本机锁必须覆盖在途 QMT 调用。
- health 缓存包含采样时间、后台状态、队列积压/溢出、pending 数、最近完整对账、tick/QMT 耗时和执行权新鲜度。

## P2：分阶段交易、配额和公平预算

HTTP → PG QUEUED → 202 → 后台预取 → QMT 参数/篮子分阶段准备 → PG 保存准备快照 → PG 最终认领 SUBMITTING → 确认提交 → 一次性执行指令 → 后续 QMT tick → 结果后台落库。

- 预取不等于认领；禁止整批预取即进入 SUBMITTING。参数读取、篮子 get/set/get 可跨 tick，最终快照和核对结果持久后才认领。
- 原子认领再次核对撤单、期限、实例代次及执行权。指令带 attempt_id、实例、代次，只消费一次；提交结果不明不能产生可执行指令。
- 本地取消先赢锁则 QMT 调用为零；SUBMITTING 后保存撤单意图等待 QMT 标识。调用结果未落库不重复派发；崩溃后按 UNKNOWN 恢复。
- 撤单同样先保存尝试再调用再记录结果；算法先停任务，再覆盖已有及晚到子委托。
- 调度预算从 process_http_requests 入口计时，覆盖 runtime.tick 和旧查询队列。撤单优先，但提交、对账、旧查询均有服务机会，轮转位置跨 tick 保存。
- WAITING_QMT_ID 不占据可执行撤单首页；候选扫描有界且能续游标，候选数与实际动作数分离，大篮子不能独占撤单器。

## P3：对账入队、退出、分批和重新唤醒

进入/维持 pending：SUBMITTING、提交 UNKNOWN、CONFIRMED 执行中/部分成交、执行 UNKNOWN，以及进入过 QMT 且撤单仍等待/执行中/结果不明的订单。

不进入：确定未调用 QMT 的 QUEUED、CANCELLED_LOCAL、提交前 EXPIRED、明确未产生任务/委托的 REJECTED。

FILLED/CANCELLED/PARTIALLY_CANCELLED/交易所 REJECTED 在最终完整核对后退出。算法或篮子 INCOMPLETE 在执行确已结束且事实完整后也退出。撤单 REJECTED 本身不能结束父单。

退出需要同时证明任务不再生成子委托、所有关联子委托结束、成交明细与累计成交一致、查询覆盖完整、没有待关联证据或未决撤单，不能只看终态枚举。

迟到回报继续入账，有新事实/缺口时在同一事务重新设 pending；重复回报不反复唤醒。重启、回报溢出、连接中断按缺口时间范围补查，包括受影响终态订单。

后台按 pending 且到期选择 → QMT 任务查询 → 后续 tick 委托查询 → 后续 tick 成交/必要历史查询 → 后台分批归并 → 逐单继续或退出。

- 按最久未尝试稳定轮转；失败记录尝试但不能伪装完整成功。
- 撤单等待关联和新缺口有优先配额，同时避免普通订单饥饿。
- 保存阶段/游标，不重叠启动轮次；1000 笔至少十批，跨 tick/事务推进。
- 同轮全账户 QMT 快照供多个业务批次复用，不能每 100 笔重复全账户查询。
- 旧轮完成前检查事实版本，不能清掉期间新回报触发的 pending。
- 100 限制业务订单数，不是 QMT 原生分页。原生查询和快照转换单独计时，不保证一次大查询在 50ms 内结束。
- 后台原始记录归并也分批，避免大事务长期持有账户行锁。

## P4：验证和交付

使用 FakeQmt 和独立测试数据库，不对业务库自动迁移、不执行真实交易。更新构建器、接口说明、部署/恢复说明及验收记录。

1. 阻塞 SQL、日志、连接或提交时，QMT tick 不等待。
2. 10/10/100 参数、预算让出、跨 tick 续跑、1000 笔轮转无遗漏和饥饿。
3. 并发幂等、响应丢失、重启只一次派发。
4. 本地取消竞争、SUBMITTING 后持久意图、部分成交撤余量和晚到成交。
5. 终态退出、迟到回报唤醒、重复不计账、旧快照不能清除新缺口。
6. 算法停任务后晚到子单、三种原生篮子准备和撤单语义。
7. 失权、授权过期、队列满、认领/调用/落库崩溃边界不盲重发。
8. STOPPING 不阻塞 QMT、不提前释放锁、重启恢复正确。
9. 真实 PG 并发、迁移和索引；ORDER/FEED 回归；Python 3.6 和 GBK 验证。
